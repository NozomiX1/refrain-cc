# E10：检索测试集

E9 C 组里书记员查了两次都没找到原型的 C 方案（M10）：M10 在同一个项目里，但检索按时间从新到旧只给 10 份，最早的 M10 被挤掉。这个测试集不调用模型，直接调用检索函数，看答案在不在结果里、排第几，每次改检索都能马上重跑。

用法：`node run.ts <cases.json>`。用例和库在 `raw/`（真实项目内容，只在本机）：`raw/wmj.db` 是 E8 wheres-my-job 回放库的副本（不能用 E9 跑过的库，里面有实验自己写的摘要），当前会话取 S4。

用例：12 个答案在很早以前的场景（早期摘要、已归档的知识、别的会话里的原话），每个 2–4 个检索词，按书记员实际的写法出（`|` 列一串同义词、混着两个字的词）；C 组里书记员真实用过的 4 条原样放进去。用例是 Claude 出的，知道答案在哪，所以单看真实那几条更可靠。

## 结果（2026-10-28）

| | 改之前 | 改之后 |
|---|---|---|
| 结果里有答案 | 17 / 27 | 25 / 27 |
| 答案在摘要或知识里排第 1 | 5 | 15 |
| C 组书记员真实用过的 3 条检索词找 M10 | 0 / 3 | 2 / 3 |
| 返回字数（中位 / 最长） | 4735 / 7430 | 7047 / 11419 |

改之前没找到的 10 次：6 次是匹配到了但被截掉（全是"两个字的词用 | 列一串"，没有相关度、只按时间排），4 次是根本没匹配到（3 次是空格要求每组都中，有一个词没对上；1 次是同义词）。

改了什么（design.md 4.7）：在代码里算 BM25，先按中了几组排；空格不再要求每组都中，没全中的标〔没中：……〕；几乎每条都有的词（单个字母 C）不算进中了几组，并在结果开头提醒；超过 limit 的折叠成标题或开头，不扔。

还没找到的 2 次：`C方案|C 方案|方案C|方案 C`（M10 里没有"方案"两个字，只有"C 为……工作台"）；`名字|起名`（摘要里写的是"名称"，要语义检索）。

变差的：已归档的 K75（阿里云服务器配置）从知识第 3–8 个降到第 5–26 个，两次在折叠的开头里（开头就是配置，能看到）。别的知识反复提到阿里云，按相关度确实更相关。

## 第二次改（2026-10-28）：两字切、知识每条一行

E9 C 组第二轮暴露了两处：一条知识的 7 个版本占了前 10 行里的 7 行（K75 被挤到第 11 个以后）；书记员写了 `阿里云 | 退订 | 退役 | 退款`，`|` 两边的空格把它拆成四个都要的词。改成：检索词由代码切（英文按单词，中文切成相邻两个字），不再有空格和 `|` 的语法；知识每条只占一行，其他中了的版本注在后面。

测试集补了 7 次检索（C 组第二轮书记员真实用过的 3 条阿里云检索、3 条直接写一句话的、1 条三版布局原型），共 34 次：

|---|---|---|---|
| 原来的 27 次里有答案 | 17 | 25 | 25 |
| 原来的 27 次里排第 1 | 5 | 15 | 17 |
| 全部 34 次里有答案 | 18 | — | 32 |
| K75 在原来 4 次里的位置 | 4、—、8、3 | 13、26、22、5 | 5、20、6、3 |
