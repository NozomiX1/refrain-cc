# E11：refrain 压缩之后恢复会话，缓存为什么接不上

## 起因

tycoon 里我退出会话、更新插件，23 分钟后用 `claude -r` 恢复，第一次请求只从缓存读了 2.3 万 token，新写了 15.3 万。CC 的记录说恢复后的对话从第 15 条消息起和退出前发的不一样，服务器还丢掉了 49 段思考。本机以前三次几分钟内恢复都接上了缓存（读 41–47 万），那几个会话里的压缩都是 CC 自己做的；tycoon 里有 refrain 接管的压缩（保留原文尾巴）。要回答的是：是不是 refrain 的压缩造成的，差在哪。

## 做法

在 `work/` 下建三个临时 git 仓库，内容是生成的三份笔记文件（每份 900 行，约 2 万 token），用 `tools/cc-start.sh` 在 tmux 里开交互式 CC（Haiku 5.5，xhigh，带思考），加载本仓库的 refrain 和 refrain-timer，数据目录各自独立，书记员触发量调到 1500 字。每组读文件、聊几轮，退出后一两分钟内用 `--resume` 恢复，再问一句，比较退出前最后一次请求和恢复后第一次请求。

- A 组：不压缩，直接退出、恢复。
- B 组：先读三份文件，等书记员整理完，`/compact`（refrain 接管，保留最后一轮），再聊两轮，退出、恢复。
- C 组：和 B 组一样，但 CC 的请求经过本机一个转发程序（`proxy.mjs`），原样存下每次请求的内容，用来比对具体差在哪。

## 结果（2026-11-08，CC 2.1.310）

| 组 | 恢复后第一次请求 | 和退出前一样的消息 |
|---|---|---|
| A 不压缩 | 从缓存读 7.3 万，新写 0.08 万 | 38 条全部一样 |
| B refrain 压缩过 | 读 2.4 万（只有系统提示和工具），新写 1.7 万；丢掉 4 段思考 | 只有前 2 条一样 |
| C refrain 压缩过 | 读 2.5 万，新写 1.6 万 | 只有前 2 条一样 |

C 组的请求内容对比：恢复后，压缩时原样保留的那条模型回复里，**思考和正文各出现了两次**；其后的消息也都跟着不同。

原因：压缩时 CC 把保留的消息另存一份副本，副本沿用原来的消息编号（`message.id`）。同一条回复在流式输出时本来就分成几行存，读回时 CC 按消息编号把这几行拼成一条；恢复会话时，压缩前的原件和压缩后的副本编号相同，被拼进了同一条，内容就重复了。CC 自己的压缩不保留原文尾巴，不会碰到。

影响：
- refrain 压缩过的会话，缓存还没过期就恢复，缓存接不上，压缩后的上下文要整段重写一次（tycoon 这次 15.3 万，按 1 小时写入价约 $1.2）。缓存已经过期再恢复，本来就要重写，没有额外损失。
- 恢复后对话里那段保留的回复是重复的，一直带到下一次压缩；重复的思考会被服务器丢掉。

## 花费

主会话三组共写缓存约 34 万 token、输出约 5 万，书记员约 $0.04，合计按 API 价约 $0.13（估的是 $0.1 以内）。

## CC 那边已有的 issue（2026-11-08 查）

都还开着，最新的回复说 2.1.318 仍有：
- [#99727](https://github.com/anthropics/claude-code/issues/99727)（10-05）：恢复时按 `message.id` 合并会跨过压缩边界，钩子凭 handle 保留的消息被成倍复制。和这里一样。
- [#105781](https://github.com/anthropics/claude-code/issues/105781)（10-28）：除了编号，保留的工具结果副本的 `parentUuid` 还指回压缩前的原件，恢复时 CC 顺着它走过边界，可能拼回整段压缩前的历史，钩子写的交接消失。
- [#95328](https://github.com/anthropics/claude-code/issues/95328)、[#106422](https://github.com/anthropics/claude-code/issues/106422)：钩子做的压缩在恢复后被撤销。

issue 里给的绕法：保留的模型回复和工具结果不带 handle 交回，让 CC 用新编号重建；代价是这些消息里的思考丢掉（压缩后服务器本来就会丢）。

## 改法和验证（2026-11-08）

refrain 压缩时，用户自己的消息照样带 handle 原样保留（没有编号，链接也对，图片能留住）；模型回复和工具结果不带 handle 交回，由 CC 重建，编号和链接都是新的。只有思考的那部分回复重建出来是一条"(no content)"，直接去掉。

- D 组（尾巴里有一次 Read 调用）：重建的回复编号各不相同，工具结果的链接指向压缩之后；恢复后 7 条消息全部和退出前一样，缓存读 3.8 万、新写 0.25 万（只是新问的那句）；压缩后问 README 写了什么，答对。
- E 组（去掉空回复之后重跑）：没有"(no content)"；恢复后 5 条全部一样，读 3.9 万、新写 0.14 万。中间一次 `/compact` 因为书记员还没整理完最后两轮被拦下，界面显示"Not compacted · refrain：暂不压缩。……"，新提示在真实界面里正常。
- 没测到：尾巴里有图片的情况（tmux 里贴不了图）。按设计，用户贴的图保留，工具结果里的图变成文字说明。

D、E 两组按 API 价约 $0.1。

原始数据（transcript、请求内容、调试日志）在 `raw/`，只在本机。

## 补充：大记录不会拼重，会丢消息（2026-11-08）

tycoon 18:51 计时器用旧版压缩过（保留的回复带 handle、沿用原编号），20:13 恢复后缓存却全部接上：恢复前 7 条消息和恢复后前 7 条一一相同，回复没有拼成两份。原因在 CC 2.1.310 读记录的代码里：记录超过 5 MB（`SKIP_PRECOMPACT_THRESHOLD = 5242880`，可用 `CLAUDE_CODE_DISABLE_PRECOMPACT_SKIP` 关掉）时，只读最后一次压缩记录之后的部分，压缩前的原件根本没读进来，也就没有可拼的。tycoon 的记录 23 MB；B、C 组只有约 1 MB，整份读入，原件和副本按编号拼成一条。

所以上面"tycoon 那次 15.3 万"的原因要改：那是 05:03 的压缩，当时记录约 22 MB，不会拼重。按 CC 记的请求结构对比，07:54 恢复后从第 16 条起少了两条：一次 Bash 调用和它的结果；保留的 7 个工具结果副本都指回压缩前的原件（#105781），原件没读进来，CC 重建时丢了这一对，后面的消息位置全变，缓存从这里断开。为什么只丢这一对没有查到底。

现在的改法两种情况都覆盖：重建的回复是新编号（小记录不拼重），重建的工具结果链接指向压缩之后（大记录不断链）。D 组验证的是小记录；大记录这边还没有用新版实测过。
