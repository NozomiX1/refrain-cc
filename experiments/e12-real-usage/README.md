# E12：tycoon 真实使用的数据（2026-11-07 至 11-11）

## 起因

refrain 里不少数字是设计时拍的：回复截断 4000 字、工具输入输出截断、每批 2 万字触发、每字 0.77 token、摘要 600 字和知识 400 字的上限、空闲压缩 15 万的下限。tycoon 已经用了 5 天，用真实数据看这些数字合不合适。只读本机的记录和数据库副本，不调模型，只输出统计。

## 做法

- `composition.mjs <memory.db 副本>`：书记员处理过的全部记录（1308 条），按类别算截断前后的字数。
- `runs.mjs <memory.db 副本> <会话的 subagents 目录>`：书记员 24 次整理，每次的输入组成、每次请求的上下文、输出、工具调用、提交的长度。
- `session.mjs <主会话 transcript>`：主会话每轮结束时的上下文、离开超过 1 小时的几次、每次压缩前后、恢复会话。

## 结果

### 1. 书记员看到的对话，各类占多少

| 类别 | 条数 | 截断前（字） | 占比 | 截断后（字） | 占比 | 被截条数 |
|---|---|---|---|---|---|---|
| Claude 的回复 | 336 | 33.3 万 | 26.0% | 33.3 万 | **63.6%** | 0 |
| 工具调用（输入） | 354 | 44.9 万 | 35.1% | 6.8 万 | 12.9% | 135 |
| 工具结果 | 354 | 45.4 万 | 35.5% | 10.1 万 | 19.3% | 154 |
| 用户的话 | 264 | 4.4 万 | 3.4% | 2.1 万 | 4.1% | 4（粘贴） |
| 合计 | 1308 | 127.9 万 | | 52.3 万 | | |

- 回复截断线是 4000 字，最长的回复 2837 字（中位 1050，p99 2537），**一条都没截**。
- 截掉的 60% 都是工具：Bash 输入输出 47.5 万字截成 13.5 万；Read 结果 17 万截成 0.9 万；**Write 和 Edit 的文件内容完全不给书记员看，只给路径**（21.5 万字，渲染规则只取 `file_path`）。
- 回复占整份输入（加上已有的知识、摘要、现状）的 37.9%；再算上书记员的说明和工具，约占第一次请求的 3 成。

### 2. 书记员每次整理

中位数：12 轮对话，这批 2.09 万字（其中回复 1.63 万），整份输入 3.8 万字，用时 2.7 分钟。

- **上下文**：第一次请求中位 5.6 万 token，最后一次 11.0 万。第一次请求里，说明和工具约 1.26 万（拟合的截距），已有记忆从第 1 次的 0 涨到第 24 次的 2.15 万字（知识 1.28 万字，线性增长约每次 +530 字；摘要列表折叠后稳定在 5–7 千字；现状约 1.5 千字）。之后变大主要是书记员自己的思考：第一次请求中位输出 2.56 万 token，整次整理中位输出 3.6 万。
- **花费**：24 次按 API 价 $0.81，其中输出（主要是思考）约 $0.44，占 54%。
- **工具**：search 30 次（13 次是"一次没查就提交"被拦下后才查），read 2 次（一份摘要、一轮记录），从没读过未截断原文。提交被拒 16 次：13 次是上面那条检查，3 次是格式问题。
- **提交的长度**：摘要 126 份，正文中位 284 字、最长 564（上限 600，碰到 0 次）；知识写入 139 次，中位 132 字、最长 314（上限 400，碰到 0 次）。
- **延迟**：用户一条消息从说出到被整理，中位 65 分钟，p75 2 小时，p90 13.8 小时（晚上最后几轮要等第二天攒够 2 万字）。

### 3. 每字多少 token

用 24 次整理拟合"第一次请求 token = 截距 + 斜率 × 输入字数"：斜率 **1.11**（R² 0.85）。另一种量法：书记员两次请求之间只多了一个工具结果时，上下文的增量 ÷ 结果字数，搜索结果 13 次在 0.89–1.23 之间，一句 45 字的确认是 1.13。tycoon 几乎全是中文，每字约 1.0–1.1 token；代码里用的 0.77 是 E7 在别的内容上量的。用到它的地方：压缩后大小的估算（摘要和简报那部分）、面板里知识的规模。

### 4. 主会话

- 587 次请求、283 轮；记忆开销比按 API 价 1.0%（$0.81 / $78），按额度口径 2.0%（$0.70 / $35）。
- 离开超过 1 小时 6 次，当时上下文：84.9 万（我手动压了）、9.6 万、20.8 万、13.3 万、36.8 万、34.5 万。
- 新规则下计时器压缩了 4 次，估算和实际（压后第一次请求，含新问的一句）：

| 时间 | 压缩前 | 估压完 | 实际 | 保留的尾巴 |
|---|---|---|---|---|

- 11-09 00:41 那次离开 15 小时，上下文 13.3 万，低于 15 万没压，回来重写了 13.4 万。

## 局限

- 只有一个项目、5 天，内容几乎全是中文的游戏设计讨论，工具用得少。换成写代码的项目，工具输入输出的比例会高得多。
- 被截掉的工具内容里有没有该记的东西，这里只统计了字数，没有逐条看。
- 每字 token 是拟合和差分得来的，没有用计数接口直接数。

## 补充（11-12）：写文件的内容、回复长度、工具的描述

**写文件的内容没给书记员，漏了什么？**（`writes.mjs`）tycoon 里 Write 和 Edit 共 63 次，涉及 30 多个文件。按文件看：
- 设计文档（rules-v0.md、logs.md、physics-v0.md、core.md、characters.md 等）：同一轮的回复都提到了文件，并讲了要点；对应的摘要也写了文件名，有的还写了提交号。抽查 rules-v0.md（5765 字）：回复讲了四个崩塌机制、内生政策收紧、规模、验证标准和三个待确认点，摘要 M28 都记下了；公式和具体数值只在文件里，摘要指向文件。这正是书记员说明里要求的"已在提交和文档里的细节只写去哪看"。
- 代码（engine.py 2.2 万字、society.py 2.6 万字、index.html 等）：回复常常不提文件名，但讲了做了什么，摘要里有文件名。代码本身不需要进记忆。
- 临时文件（scratchpad 里的草稿）：回复没提，摘要也没有，不需要。
结论：没有发现因为看不到文件内容而漏记的决定。

**回复要不要截。** 本机全部 26 个主会话、2757 条回复，超过 4000 字的只有 2 条，一共截掉 2890 字；p99 2426 字，最长 5637。4000 这条线几乎碰不到，只防万一。

**工具的描述。** Bash 每次调用都带一句描述（237 次全有，中位 48 字，最长 82），比如"Verify downloaded file sizes against Hugging Face"。现在渲染只取命令（截成开头 250、结尾 50），描述丢了；134 次命令被截的，看到的是半截脚本。把描述放在命令前面，每次多约 50 字，5 天共约 1.1 万字（+2%）。

## 补充（11-12）："一次没查就提交"那条检查值不值（`checklist.mjs`）

24 次整理里 13 次被这条检查拦下。拦下以后：
- 2 次直接确认（`confirm`），没改；
- 4 次查了一两次，又把一模一样的整份重交了一遍（说明里写的是"都没有的话只写 confirm"，查过以后没东西要改时它没这么做）；
- 7 次重交时改了一些：多是摘要和知识正文的措辞，知识的操作（新建还是更新哪条）只有 1 次变了：多更新了一条已有的 K78。
代价：拦下后的那几步共输出约 14 万 token，约占书记员花费的 9%；一模一样重交的 4 次就占了约 6 万。

## 补充（11-12）：拿一条知识的全文去搜，能不能找到它对应的旧条目（`likematch.mjs`）

设想的用法：书记员看不到全部知识时，由程序拿它这次要写的知识去搜已有知识，把可能相关的递给它。担心的是知识正文一两百字，当搜索词太长。用书记员自己做过的"更新"当标准答案：每次更新都写明了改的是哪一条，拿新版正文去搜当时所有有效知识，看那一条排第几。

| 数据库 | 更新次数 | 全文当搜索词：第 1 / 前 3 | 只用第一句 | 只用最少见的 20 个词 | 最不像旧版的四分之一：全文前 3 |
|---|---|---|---|---|---|
| tycoon | 58 | 58 / 58 | 57 / 58 | 57 / 58 | 15/15（词重合 ≤ 41%） |
| wheres-my-job（E10 回放库） | 179 | 175 / 178 | 174 / 179 | 175 / 177 | 44/45（词重合 ≤ 30%） |

长搜索词没有问题：BM25 对长查询相当于算"两段文字有多像"。局限：更新通常保留了旧版不少说法，比"换了说法重写一条"容易；中英文、同义词换着说的情况没测；知识只有一两百条，库大了排名会更挤。
