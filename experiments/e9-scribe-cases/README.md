# E9：书记员的定点小测

E8 的回放每次要几小时。大多数问题只出在少数几批对话上，而回放时每次整理的完整输入都存在数据库里，所以可以把那一刻单独拿出来重跑：`case.ts` 把回放的数据库复制一份、退回到那一批之前（之后写的摘要、知识、现状、原文全删，全文索引重建），只让书记员处理那一批，重复几次，结果不写回原库。输入可以是回放里的真实一批，也可以是编的几行对话（接在某个会话后面）。用例文件和结果在 `raw/`，含真实项目内容，只在本机。

用法：`node case.ts <case.json> <输出目录> [推理强度] [替代的 scribe-system.md]`。小测每次只花几美分，允许同时跑 3 个；整段回放仍一次一组。

## 教训：挑出过错的样本重跑，必须有对照

挑"出过错"的样本来测一个改动，重跑时大多数会自己变好（回归均值）。不跑对照，会把运气当成改动的效果。下面两组都是靠对照才没有误判。

## B：知识越写越长（2026-10-28）

E8 high 那一遍有 3 次失败，都是更新知识后正文超过 400 字、3 次没压下来（K17、K22）。当时以为原因是"每次更新都往正文里塞原话"（K7 就是这样），于是提示词加了"更新时不堆原话"。

挑了 5 批（第 21、23、25、40、43 批，3 批当初失败、2 批写到 390 字左右），新旧提示词各跑 2 次，Haiku high：

| | 新提示词 | 旧提示词（对照） |
|---|---|---|
| 失败 | 0 / 10 | 0 / 10 |
| 超长被退回 | 7 | 7 |
| 更新后正文中位长度 | 331 字 | 333 字 |
| 350 字以上 | 10 / 32 | 12 / 32 |
| 额度（API 价） | $0.59 | $0.57 |

- 那句提示词没有作用；当初 3 次失败多半是运气（重跑 20 次没有一次失败，超长都在 3 次内压了下来）。
- 变长的主要原因不是原话：两组每条平均引用不到一句原话。最长的 K17（397 字）是一张文档清单，每多一份核验文档就加一项。
- 决定：那句保留（不影响），超长时的回执改成写明要删多少字、清单只写去哪看、原话优先留最新的一句（待下一轮观察）。

## A：现状"改了却当成新增"——对照（2026-10-28）

E8 里书记员改现状的某一项时，常把新内容写成新增、没标 `from`（low 47 次里 21 次，high 50 次里 8 次），都被"每项都要交代"的校验退回、补上了。挑了 10 批出过这个错的（high 第 4、7、19、25、29、30、37、42 批，low 第 18、40 批），用现在的格式、Haiku high 各跑 1 次：

| | 结果 |
|---|---|
| 又出现"改了却当成新增" | 1 / 10（第 25 批） |
| 退回 | 3 次（1 次是上面这个，2 次是知识超长） |
| 失败 | 0 |
| 额度（API 价） | $0.27 |

在 high 下这个错并不常见。下一步仍要测新格式（现状改成和知识一样的操作列表：keep / update / close / create），理由是两套写法统一，书记员只需要会一种；判定标准是不比现在差就保留。

### 新格式（2026-10-28）

同样 10 批，各跑 2 次，Haiku high，同时还换了新的回执（用编号和正文开头指认出错的那一条；知识超长写明至少删多少字）：

| | 新格式（20 次） | 旧格式对照（10 次） |
|---|---|---|
| 失败 | 0 | 0 |
| 改了却当成新增（旧项没写，被退回） | 0 | 1 |
| 新格式写错（create 带序号、keep 带内容） | 0 | — |
| 漏网的重复项（新增一项、旧的同一件事又保留） | 0 | 0 |
| 知识超长被退回 | 4 次（20%） | 2 次（20%） |
| 超长后重交一次就改好 | 4 / 4 | 2 / 2 |
| 每次额度（API 价） | $0.021 | $0.027 |

- 漏网重复项是回执拦不住的那种错，用 `a-dups.ts` 逐项比对：新增的项和上一版原样保留的项相似度过 0.4 的列出来人工看。新格式 2 处（第 7 批两次），都是旧的"正式代码先不改"和改写后的授权范围，相关但不是同一件事。
- 第 7 批两次都把授权的改动正确地写成了 `update`。
- 决定：保留新格式。20 次只能看出大的差别，结论是"没变差"，不是"更好"。
- 超长退回的比例没变（都是 K17 文档清单、K30 路线、K6 这几条老面孔），新回执要删的字数从 9 到 80 字不等，都一次改好；新旧回执在这一点上看不出差别。

## C：检索（2026-10-28）

E8 的回放里检索几乎为 0。逐批核对后，那段数据里每次需要的信息都已经在输入里（知识全文、本会话的摘要、这一批里助手当场的解释），用不着查。需要查的只有两种：已归档的知识，和没沉淀成知识、只在别的会话或很早的摘要里的细节。用例：重提已归档的阿里云服务器（编的对话）、"改回最早那版原型里的 C 方案"（编的对话，C 方案只写在 Pi 会话的一份旧摘要里）、10-11 用户在 CC 里说"先别动手，讨论一下"（真实一批，之前同类的话都在 Pi 会话里）。

三个场景各跑 3 次，Haiku high，额度 $0.23（API 价）。判读用 `c-report.ts`，逐次看调用了什么、查到什么、写了什么：

| 场景 | 查了 | 查到并用上 | 情况 |
|---|---|---|---|
| 已归档的服务器（K75） | 0 / 3 | 0 / 3 | 两次在摘要里引了输入里看得见的退订摘要；第 1 次自己写了"具体的配置参数没有在这段里说明"，发现了缺口却没去查。搜"阿里云"或"阿里云 服务器"都能查到 K75，查不到不是原因 |
| 原型 C 方案（M10） | 2 / 3 | 0 / 3 | 查了，没查到。M10 在同一个项目里，但检索词太宽（`C 方案\|原型` 是"含 C 并且含方案或原型"，单个 C 几乎什么都匹配），摘要按时间从新到旧只给 10 份，最早的 M10 被挤出去；结果只写"找到 10 份摘要"，不提示还有更早的。搜"原型 三版"能直接查到。没查到时都如实写了"没找到"，没有编 |
| 一次性要求反复出现（真实第 102 批） | 1 / 3 | 1 / 3 | 查了的那次做得完全对：新建推断类规则"用户习惯先讨论、确认后再动手"，出处带上 S1、S2、S4 的 7 处。另两次没查，只写进摘要 |

- 查了 3 / 9，查到并用上 1 / 9。
- 第 102 批里有 4 个账号密码一类的字符串，9 次都没有写进记忆（`secrets.json` 比对，只计数），摘要里写的是"含明文密码，不记录"。
- 两类问题：书记员该查的时候不查（提示词）；查了但结果把早期的内容挤掉、又不说还有更多（检索工具）。
