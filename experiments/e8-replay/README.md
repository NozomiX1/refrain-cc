# E8：回放本会话，直接对答案

对应 design.md 8.4 的离线回放评测，先用本项目的设计会话。要回答的是：书记员面对真实的长对话，记下了多少、记得对不对、现状准不准、花多少。E7 的问答题对漏记不敏感（漏掉的从原文里也能搜到），这次不答题，直接拿书记员写下的摘要、知识、现状对照事先写好的标准答案。

## 做法

- **素材**：本会话（10-22 到 10-27，322 轮，压缩过 7 次），截到用户说"同意，做吧"（定下本实验方案）为止。整段从头回放，和真实使用一样从零攒起。原始数据在 `raw/`，只在本机。
- **考题范围**：只考 10-24 之后的内容。前 124 轮（到 10-23）是 E7 用来调提示词的，不考。
- **标准答案**（`raw/key.json`，哈希在 `key.sha256`，看结果前提交）：从 log 整理，用户过目过。事件 72 个；知识 42 条（核心 25 条，改过主意的 8 条，核心里 22 条附理由）；现状（已完成 5 项、待办 9 项）；数字 8 条。
- **回放**：`../e7-scribe/replay.ts`，真实核心程序，书记员 Haiku low，2 万字触发，每批最多 5 万字，一次只跑一组。
- **判分**（`match.ts`）：Sonnet medium 按标准答案逐条判，三次调用（事件对摘要；知识和数字对知识、摘要；现状对最后的现状），Claude 对照数据库抽查。理由分三级：写在知识里、只在摘要里、都没有。编造率沿用 e7 的 `facts.ts`（只在第一遍跑）。

## 结论

1. **召回不是问题。** 两遍都没有丢失的知识，事件几乎全部写到，改过主意的都换成了新版本、旧版本归档并写明原因，大部分理由写进了知识。数字类多半只在摘要里，需要时靠检索。
2. **问题在规模。** 原版 5 天一个项目，简报约 1.6 万 token，越过 1.5 万的提醒线。大头是本项目的背景和决定（56 条，近 1 万字）和项目现状（32 项）；关于用户的知识只有 10 条（约 1.1k token）。
3. **现状为什么涨：** 提示词自己把拿不准的事往"待核实"里推（32 项里 15 项待核实）；项目往前走时旧事是悄悄过时的，没人专门说"不用做了"，书记员只在对话明说做完时才关；每项都要交代去向，"沿用"最省事。改法（2026-10-27）：待核实只放卡住接下来工作的事、已做的决定写成知识、每次重写把上一版整份过一遍（做完的、过时的、久未提及又只是顺带提到的关掉，用户自己提的待办不因久未提及关掉）、代码上限 20 项。改后停在 18 项，放弃的项都写了理由（如"已过时：简报已改走 SessionStart"）；仍高于"十项左右"的目标，但这个项目这时真待办就有十几项。
4. **知识分层注入**（design.md 5.5）：只在简报里折叠本项目的背景和决定（超过 4000 字后较早的只列第一句），规则、参考、目标、关于用户的永远全文，书记员的输入不折叠。依据是"模型会不会知道自己该去查"。同一份第一遍数据，折叠后约 1.27 万 token。改后知识多了 16 条（现状里的决定和已验证的结论挪进了知识），简报仍约 1.29 万 token。
5. **失败**：每遍 2 次，失败的那批下一次整理会补上，不丢内容。三种原因：现状太长，3 次都没交代全旧项的去向（第一遍）；书记员说输入里没有要处理的对话，其实有（两遍各一次，一次说它只看到"已有的记忆、MEMORY.md 和环境信息"）；一次 API 卡住 15 分钟超时。第二种的一部分是实验环境造成的：回放在本仓库里跑，CC 自带的 auto memory 把本仓库的 MEMORY.md 也塞进了书记员的输入；真实使用时 refrain 会关掉 auto memory。之后 `replay.ts` 给书记员关掉了 auto memory（实测有效）。

## 没测的、留给以后的

- 折叠以后主模型会不会去查：放进压缩保真率实验，作答用 Opus。
- 两种设置各只跑了一遍，差别里有波动。
- 新提示词漏掉了"已定做法还没实现"的待办（写成知识后待办没留）：看完结果后提示词补了一句"决定了、但还没落实的，知识写决定，现状里留一项待办"，还没重跑验证。
- 别的项目（wheres-my-job、Pi 的会话）的知识分布可能不同，折叠的预算到时再调。
