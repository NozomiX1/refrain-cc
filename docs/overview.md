# refrain 总览

> 一页看懂 refrain 现在是什么样、做到哪了。细节以 [design.md](design.md) 为准；为什么这样定、推翻过什么，见 [evolution.md](evolution.md)；逐日的讨论记录在 [log.md](log.md)。每做完一件事就更新这一页。
>
> 更新于 2026-10-26。

## 是什么

一个 Claude Code（CC）插件，让 CC 跨会话、跨项目地记住两类东西：**我是谁、喜欢怎么做**；**每个项目进行到哪了**。取代 CC 自带的 auto memory。

和别家不同的地方：每条记忆都带着出处，标明是我的原话、推断还是观察；压缩不调模型（交接是拼出来的，约 5 毫秒）；记忆的开销能量化。

## 怎么运转

```
我和 CC 对话（主会话）
  │ 每轮结束：新内容攒够 2 万字？
  ▼
书记员（后台子 agent，Haiku，推理强度 high）
  │ 读这批对话 + 已有的知识、摘要、现状 → 一次 submit 交上来 → 校验，不过就退回重交（最多 3 次）
  ▼
SQLite（~/.refrain/memory.db）：知识（带版本）、摘要、现状、原文索引
  │
  ├─► 新会话 / /clear / 压缩之后：简报（知识 + 现状）经 SessionStart 只给主会话
  ├─► 手动 /compact 或空闲压缩：交接（本会话的摘要 + 最后一段原文原样保留）替换上文，不调模型
  └─► 主模型需要以前的细节时：search / read 检索摘要、知识和原文
```

- **主模型只干活，不写记忆**；写记忆的只有书记员。我要改记忆就在对话里说，书记员下次整理时处理。
- **CC 的自动压缩和它自带的空闲压缩被拦下**；空闲压缩由配套的小插件 refrain-timer 按我们的条件发起。
- **会话关掉时没整理完的尾巴**，由同一项目里下一个会话的书记员补上（那个会话 1 小时没动静就算关了）。
- **压缩不会明显变小时不压**（上次压缩后书记员还没整理过，或压完超过一半），对话里显示一行原因，不交给 CC 原生压缩。
- 状态栏显示书记员在不在跑、花了多少；`/refrain` 打开面板看当前的记忆。

## 定下来的数

| 项 | 值 | 依据 |
|---|---|---|
| 书记员的模型和推理强度 | Haiku 5.5，high | E7：Haiku 和 Sonnet medium 的答题分在波动之内，额度约是它的 1/7；E8：high 记下核心知识 8/8，low 5/8，额度约 2 倍 |
| 触发量 / 每批最多 | 2 万字 / 5 万字（渲染后） | E7：6 万字省额度但知识少四分之一、更容易交白卷；5 万字保证单次请求不越过 Haiku 的价格线 |
| 每次至少写一份摘要 | 是 | E7：书记员交过白卷 |
| 提交被退回 | 最多重交 3 次；同一会话连续失败 3 次就暂停 | |
| 摘要折叠 | 最新 8 份全文，更早的每 8 份折成标题，标题最多 160 条 | 待 E6 调 |
| 空闲压缩 | 缓存过期（1 小时）后、上文 ≥ 15 万 token、上次压缩后整理过、压完不超过上文一半 | 2026-11-08 下限从 6 万提上来，见 design.md 4.5 |
| 书记员的额度消耗 | 每次整理约 $0.02–0.03（high，只算输入、缓存写入和输出；一次都没查时多问一次，约多 40%） | E7 的额度核对、E8、E9 |

## 代码和测试

- `hooks/register.tsx`：mod，接 CC 的事件、注册工具和书记员、面板、状态。
- `core/`：Node 核心程序，读原文、书记员的准备和校验、存储、简报和交接、检索。零依赖，Node ≥ 24。
- `timer/`：refrain-timer，只负责空闲压缩的计时。
- 本机试用：refrain 装在 ~/lab/tycoon（11-12 起暂停）和 ~/lab/refrain（作者的另一个项目），都是 local 范围，共用同一个插件缓存，给其中一个更新另一个也跟着变。插件源是 git archive 导出的干净副本 ~/.claude/plugin-src/refrain，不是工作目录（CC 会把目录插件源整个复制进缓存，连 raw/ 的真实数据）。改了代码、提交以后，跑 `tools/update-local-install.sh <项目目录>`（首次安装也用它），下一个会话生效。
- 测试：核心 52 个（`npm test`），mod 5 个（`npm run test:mod`）。检索另有一个不调用模型的测试集（`experiments/e10-search/`，用例是真实数据，只在本机）。CC 自检清单 9 项在 2.1.310 上手动验证通过；CC 固定在 2.1.310，不自动升级。

## 进度

**做完了：** 第一版的全部部件（读取器、书记员、存储、简报注入、交接、检索、面板、状态栏、备份、`/refrain resume`、补尾巴）和 refrain-timer。

**实验做过的：**
- e1 消融：两三天的跨度上，问答题"只检索原文"不输 refrain，但 refrain 每次作答便宜约 5 倍、不用来回查；任务题（不问也该用上以前定的规则）refrain 明显更好。
- E7 书记员：定了模型、强度、触发量、上限；顺带查清了订阅额度怎么扣、书记员的缓存为什么命中不了。
- s1–s3 演练、e2 探测、s2 录制测试样本：端到端跑通，查出并修了一串 bug（压缩后误撤销、书记员收到主模型的简报、书记员从不收尾……）。
- E8 真实项目回放：用两个真实项目（本项目的会话、一个求职网站项目的 CC 和 Pi 会话）从头回放书记员，逐条核对知识、现状、摘要。据此改了现状规则、简报折叠、书记员改用 high。
- E9 定点小测：把回放库退回到某一批之前，只重跑那一批。A 组（现状"改了却当成新增"）、B 组（知识越写越长）、C 组（需要查以前记录的场景）。
- E10 检索测试集：不调用模型，直接看答案在不在检索结果里。检索因此改成按相关度排（中文两字一段、BM25），34 次检索里找到的从 18 次到 32 次。


**发布前要做：**
- README、LICENSE（MIT）、`marketplace.json`、refrain-timer 的依赖声明、给别人用的状态栏脚本：已做（2026-10-27）；
- 已发布（2026-10-27）：<https://github.com/NozomiX1/refrain-cc>（2026-11-12 从 refrain 改名，名字留给作者的另一个项目），公开副本的工作目录在 `~/lab/refrain-cc`。以后更新：重新导出到临时目录，覆盖到 `~/lab/refrain-cc`（保留它的 `.git`），追加一个提交再推送，不重建、不强推；

- 开源前清理个人信息（哪些文档公开，待我定）；
- 正式版是否全局关掉 auto memory（现在只在用到的项目里关）。

**待做：**
- 状态栏和面板加一个"额度口径"的花费（只算输入、缓存写入和输出），和现在的 API 价并列；
- 交接、search、read 的返回和标准样例逐字比对的测试；
- 剧本测试（构造的小项目，可公开的回归测试）。

**实验和评测（都要花额度，跑之前先说）：**
- E6：摘要的粒度和长度；
- 离线回放评测：编造率、对齐成本、压缩保真率、接续准确率，对外展示的主要数字；
- 演练项目：比如给 Pi 做一个 subagent，跨几个会话真实地跑一遍；
- E7 剩下的：裁剪上限（不裁剪对比）、跨会话时书记员会不会去搜、B9（"待定"的边界）。
- 回归回放：wheres-my-job 整段用 10-28 以后的代码重跑（跨会话，约 $5）；Pi 的 subagent 等会话（~/lab，不属于任何项目，改主意最密集，约 $2.2，先整理标准答案给我过目）。
- Sonnet 对比：不整段跑（现有测试已顶满，分不出高下），把 Haiku 出错的批次攒起来，用 Sonnet 定点重跑（E9 那样，每次约 $0.2）。现在攒到的：服务器场景查到了没用上、回归回放里现状没结束的几批。

**待验证：** fork 之后书签和临时要求怎么接；补尾巴、白卷退回后重交在真实使用中的表现；CC 自带空闲压缩的触发值；D4（关掉后恢复、缓存已过期时，能否在第一次请求前换成交接）。

**还缺的证据：** 机制大多有来源（design.md 附录"机制的来源"），但 refrain 整体"有没有用"还缺数据：现有评测只用了一两个会话、两三天的跨度。优先补：压缩保真率（交接对 CC 原生压缩）；编造率扩大样本并人工抽查判分；真实使用几周的对齐成本和开销比；多个时间点的离线回放（含 CC auto memory 基线、任务题扩到二三十道）；公开的剧本基准。

**推迟（有真实需要再做）：** CC 自检脚本和"未自检"提示；平时使用中的被动检查；回滚时 global 知识被别的会话改过的标记；以及 design.md 第 9 章列的其余各项（推断的确认、硬约束用 hook 强制、冷启动、Dreamer、脱敏……）。

## 已知问题（2026-10-28）

按记忆系统的链路排：写进去、找出来、用起来、长期维护。证据和数字见 log.md 和各实验的 README。

**找出来、用起来（检索链路，RAG 和记忆系统共同的核心难题）：**
1. **不知道该查。** 同一场景、同样的输入，有时查有时不查（E9 C 组第一轮，需要查的 9 次只主动查了 3 次）。书记员加了提交时的清单（一次都没查就先问一次），第二轮 9/9 都查了，但每次整理额度多约 40%。**主模型没有任何兜底**：它和用户对话时没有"提交"这个节点可以拦下来问，E1 里简报没有的内容它直接答不知道。这是目前最大的未解决问题，简报折叠得越多越依赖它。可能的方向：每轮由代码先检索一次推送进上下文、在关键时刻提醒、继续靠简报和提示词，都还没讨论。
2. **查不好。** 字面检索基本解决（E10）。没解决的：同义词（"名字"对"名称"）要靠语义检索，需要额外的模型和依赖，暂不做；测试集是 Claude 出的，真实的检索词只有十几条；检索在代码里全量扫描，数据大十倍要建索引。
3. **查到了不用。** 答案已在结果第 5 个、全文可见，书记员读了却没用上（E9 服务器场景 3 次里 1 次）。没有处理办法。检索结果为了不挤掉答案加长了（中位约 4700 字到约 8500 字），越长越容易漏看，两者互相拉扯。
4. **用了过时的。** 同一件事有几份摘要时，早的写"待定"、晚的已经定了。靠"以时间靠后的为准"的提示缓解；改成按相关度排后，早的也可能排在前面，最近没再测。

**写进去（书记员的质量）：**
5. **知识越写越长。** 约 20% 的整理里有知识超过 400 字被退回，总是那几条清单式的参考类知识（每多一份文档就加一项）。每次都能压回去，根子没解决。
6. **现状"改了却当成新增"。** 改成操作列表后，代码能拦的那种（旧项没交代）拦住了；拦不住的那种（新增一项、旧的又 keep）代码看不懂是不是同一件事，只能抽查，小测里没发现。
7. **该记的没记、归纳过度。** "先讨论再动手"这类习惯，靠检索加清单在小测里 3 次有 2 次写出了推断规则，整段回放没验证。查得多以后推断规则也变多，目前看到的都合理，规模大了会不会把偶然的话归纳成习惯，还不知道。
   - 判断标准（10-28 定）：推断写得窄可以接受（推错了比漏掉更伤）；真正的问题是两类，一是用户明确说出的偏好没记下来，二是在原话之外推出一条新规则还当成用户的要求。~/lab 回放里各有 1 例："希望模型尽量自己做完、几乎不来找我"只被收进权限那条；从"讨厌 superpower 臃肿"推出"不要整包推荐 skill"，和后来整套装 Matt 的 skill 矛盾。只有一例，先不改提示词，以后判分专门统计这两类。
8. **凭据。** 密码从没写进记忆；E8 有一次 IP 出现在现状的 URL 里，提示词已补，没再验证。原文检索可能带出密码，第一版不脱敏，这个风险已接受。

8b. **裁剪（低优先级，没研究过）。** 书记员看的是裁剪后的文字：用户的话和 Claude 的回复是全文（超过 500 字的粘贴才切中间），工具的输入输出只留开头和结尾各约 200 字，约占原文四分之三的字被切掉；约 300 次整理里只读过 2 次未裁剪的原文。判过分的三次回放里，没记下的条目没有一条是裁剪造成的。不裁剪的对比输入会变成三到四倍，多出来的主要是代码和文件内容，等真实使用中碰到因裁剪记错的例子再测。

**长期维护：**
9. **增长。** 简报里较早的背景、决定和参考会折叠成开头一句，被折叠的要靠主模型主动去查，又回到第 1 条。归档知识和摘要一直涨，检索结果也跟着变长。
10. **成本。** 书记员改 high 约 2 倍，清单再多约 40%，检索结果也变长了；叠在一起的总额度还没整段回放实测过。

**和 CC 的配合：**
11. **refrain 压缩过的会话，恢复时缓存接不上**（2026-11-08，E11）。CC 把压缩时保留的消息另存副本、沿用原来的消息编号，恢复会话时把原件和副本拼进同一条，保留的那段回复内容重复，开头之后就和退出前对不上。缓存没过期就恢复，要多重写一次压缩后的上下文；过期后恢复没有额外损失。是 CC 读取记录的问题（#99727、#105781，还开着）。已绕开：模型回复和工具结果不带标记交回、由 CC 重建，只丢思考（压缩后本来就丢）和工具结果里的图片；实测恢复后缓存接上。

**评测本身的缺口：** 小测样本小（10 批各 2 次、3 个场景各 3 次），只看得出大的差别；10-28 的三处改动（现状格式、清单、检索）还没合在一起整段回放过；主模型那一侧（会不会用简报、会不会查、检索词怎么写、压缩后还记得多少）几乎没测；还没有真实使用。
